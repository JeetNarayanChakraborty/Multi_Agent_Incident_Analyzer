Project Blueprint: Production-Grade Multi-Agent Incident Triage

Overview
This framework is an enterprise-ready incident triage system built with Java and Spring AI. 
It utilizes a central orchestrator and specialized worker agents to investigate backend latency spikes dynamically. 
By combining parallel data gathering with a sequential ReAct (Reason + Act) loop, 
the system identifies root causes across logs, databases, and code repositories. It is fortified 
with strict access controls, semantic ORM mapping, and context-window optimization 
to handle real-world data at scale.



1. Cloud Infrastructure & Security Guardrails
To operate safely in a production environment, the framework enforces 
strict read-only boundaries and scoped access:

Orchestrator Agent(Gemini API): The central decision-maker. Configured with a max_iterations = 5 circuit breaker 
to prevent infinite loops and runaway API costs.

Log Agent(Axiom): Connects via an API token scoped explicitly to query operations.

Database Agent(NeonDB): Connects to serverless PostgreSQL using a strictly 
configured Read-Only Database User. The tool methods contain application-level regex 
validation to outright reject any destructive commands (e.g., DROP, ALTER, UPDATE) 
before they hit the database driver.

Deployment Agent (GitHub): Authenticates using a scoped Personal Access Token (PAT) 
restricted to read-only access for repository metadata and pull requests.



2. Context & Data Management
The agents utilize server-side aggregation and semantic mapping to 
prevent the LLM from being overwhelmed by raw production data.

Context Window Optimization: Instead of fetching raw log lines, the Log Agent constructs 
dynamic aggregation queries (e.g., executing an Axiom APL query to return 
"Count of HTTP 500 errors grouped by exception type in the last 15 minutes"). 
Only the aggregated statistical summary is returned to the LLM.

Handling Abstraction (ORMs vs. SQL): The database executes raw SQL, but production code uses Java Entities (Hibernate/JPA). 
The framework utilizes a semantic mapping layer. When the Database Agent discovers a locked table (e.g., orders), 
the Git Agent dynamically maps this to the corresponding application abstraction (e.g., OrderEntity.java or V1__Add_Orders.sql) 
before searching the commit history.



3. Execution Flow: The Dynamic ReAct Loop
The architecture resolves issues by constructing dynamic tool parameters based on real-time alert data.

Loop 1: Gathering Symptoms (Parallel Sweep)
A webhook triggers the Orchestrator with an alert payload containing dynamic 
variables (e.g., service="order-service", timestamp="2026-08-19T14:30:00Z"). 
The Orchestrator injects these parameters into parallel tool calls. 
The Log Agent executes an aggregation query for exceptions occurring after the timestamp. 
Simultaneously, the Database Agent queries pg_stat_activity for active transactions running longer than 5 seconds. 
The Log Agent returns a summary of connection pool timeouts, while the DB Agent returns the exact hanging query.


Loop 2: Finding the Origin (Sequential Deep Dive)
The Orchestrator evaluates the parallel findings. Deducing that the hanging query 
caused the connection timeout, it passes the locked table name to the Deployment Agent. 
The Deployment Agent maps the raw table name to its ORM entity and dynamically queries the 
GitHub API for commits merged within the last 24 hours that modified that specific entity. 
The Deployment Agent returns the metadata for the offending Pull Request.


Loop 3: Synthesis and Resolution (Termination)
The Orchestrator evaluates the complete state. A causal chain is established: 
The recent Pull Request altered an entity, generating an unindexed 
database query, which locked the database, exhausted the connection pool, 
and triggered the alert. Recognizing no further data is needed, the system generates a final 
Markdown-formatted Root Cause Analysis report and safely terminates the loop.


Automated Escalation & GitHub Issue Publication
Upon synthesizing the Root Cause Analysis (RCA), the Orchestrator 
invokes the GitHub Issues API. The complete markdown report 
is published as a labeled production incident issue with 
executable remediation scripts.
